# Hill-Climbing Working Copy, Finalize & Publication Protocol

> **Parent Skill Reference**: This reference defines the working-copy (`<context_set_id>` vs. `<context_set_id>_draft`) server lifecycle, the **Finalize** workflow (Steps 1–5), and replacement/deletion safety rules for [`context-engineering-hillclimb`](../SKILL.md), executed immediately when a stopping condition fires (`## Converged: <reason>`) or after `## User Stop` when the user asks to finalize.

## Working Copy & Server Lifecycle (`<context_set_id>` vs. `<context_set_id>_draft`)

Local files (`vN/context_set_vN.json`) are the durable source of truth. The Context Set server holds **one working copy** for the whole run (`v0..vN`); iteration `N` overwrites it with `vN/context_set_vN.json`, evaluates against it, and moves on — there is no per-iteration delete and nothing is re-downloaded mid-run. Which resource is the working copy depends on whether the final name already existed when `context-engineering-init` ran (read `Draft Context Set resource` from `experiment_state.md`):

| Case | `Draft Context Set resource` in `experiment_state.md` | Working copy for `v0..vN` | End of run (`Finalize`) |
| :-- | :-- | :-- | :-- |
| **Fresh** — `<context_set_id>` did not exist at init | `(none — new context set; iterations upload to the final name)` | the bare `<context_set_id>` itself (include `databases` derived from `## Active Database` + `tools.yaml`) | re-upload the best `vK` to the same name, run the holdout test on it, done. No `_draft`, no delete. |
| **Existing** — `<context_set_id>` existed at init (in-place improvement of a user-supplied resource, or a reused name) | `…/<context_set_id>_draft` | `<context_set_id>_draft` (**omit `databases`** so temporary draft iterations do not appear in the Cloud Console DB Studio UI); the existing set is **never written during the loop** | re-upload the best `vK` to the draft, run the holdout test on the draft, then a **mandatory HITL** (even with `Auto-approve uploads: true`): show previous vs new results and ask whether to replace the existing set — asked **only if holdout verdict is `PASS` and `vK` beats `v0`**. Delete the draft afterwards either way. |

## Finalize Steps (1–5)

**Finalize** runs after `## Converged`, or after `## User Stop` when the user asks to finalize. Order matters: the holdout test runs on the candidate **before** anything existing is replaced.

1. **Pick the candidate**: the best-scoring iteration `K` from the Iteration Log (ties → earliest). Append `## Finalizing: vK` to `experiment_state.md`.
2. **Put the candidate in the working copy**: if `K ≠ N` (the working copy holds the last iteration, not the best), read `vK/context_set_vK.json` and `upload_context_set(... contextSetId=<working_copy>, contextPayload=<exact file contents>, description=<experiment + score>, databases=<derived from the Active Database source + tools.yaml in the fresh case; omit databases when <working_copy> is <context_set_id>_draft>)` → poll gate. The re-upload is unconditional on a resume (never infer what the server holds). The working copy now *is* the candidate.
3. **Holdout test on the working copy**: load [`../../context-engineering-workflow/references/holdout-evaluation.md`](../../context-engineering-workflow/references/holdout-evaluation.md) and execute the **Holdout Evaluation & Generalization Reporting Phase** with the working-copy resource as the candidate. It writes `final_evaluation_report.md` and `## Generalizability` to `experiment_state.md` and returns the verdict and the holdout score. Do not print the on-screen card yet when a replacement or seed-sync decision is needed in step 4 — ask the user first.
4. **Finish per case:**
   - **Fresh case** (`<working_copy>` = `<context_set_id>`): the candidate is already live under `<Final Context Set resource>`.
     - **If seeded from an existing server Context Set** (`Seed Context Set resource` is a `projects/...` resource distinct from `<Final Context Set resource>`, e.g. in a cloned experiment) **and the holdout verdict is `PASS` and `score(vK) > score(v0)` on the hillclimb split** — **mandatory HITL, regardless of `Auto-approve uploads`:**
       1. First evaluate the original `<Seed Context Set resource>` (`v0`) once on `splits/holdout.json` (output directory `<hillclimb_root>/holdout_eval_v0/`) so you have `<holdout_score(v0)>` alongside `<holdout_score(vK)>` for a complete before/after comparison.
       2. Present the side-by-side comparison (`v0` on `<Seed Context Set resource>` vs `vK` on `<Final Context Set resource>` across both Hillclimbing and Holdout splits) and ask:
          *"This candidate (`vK`) passed the holdout generalizability check and is **already uploaded to the new context set `<Final Context Set resource>`** (improving hillclimbing accuracy from `<score(v0)>` to `<score(vK)>` and holdout accuracy from `<holdout_score(v0)>` to `<holdout_score(vK)>` — **PASS**). Do you want to also upload its contents (`vK`) to the original context set `<Seed Context Set resource>`, or keep things separate in the two different context sets?"*
       - **Upload to original (`<Seed Context Set resource>`)** → call `get_context_set` on `<Seed Context Set resource>` to read its existing `databases` list and check for concurrent `payload` updates since `v0` (warn and confirm if changed); then read `vK/context_set_vK.json` and call `upload_context_set` targeting `<Seed Context Set resource>` with `databases=<append: existing databases from get_context_set plus this experiment's derived database, de-duplicated>` → poll gate. Replace `## Finalizing` with `## Final: <Final Context Set resource> (from vK, score <S>); also uploaded to original seed <Seed Context Set resource>` plus the upload operation names.
       - **Keep separate** → leave `<Seed Context Set resource>` untouched and replace `## Finalizing` with `## Final: <Final Context Set resource> (from vK, score <S>); original seed <Seed Context Set resource> kept separate` plus the upload operation name.
     - **Otherwise** (no server seed, holdout verdict is not `PASS`, or `vK` did not beat `v0`): do **not** offer to upload to `<Seed Context Set resource>`; replace `## Finalizing` with `## Final: <Final Context Set resource> (from vK, score <S>)` plus the upload operation name. Nothing to delete.
   - **Existing case** (`<working_copy>` = `<context_set_id>_draft`) — **mandatory HITL, regardless of `Auto-approve uploads`:**
     - If **the holdout verdict is `PASS`** and `score(vK) > score(v0)` on the hillclimb split, first evaluate `<Final Context Set resource>` (`v0`) once on `splits/holdout.json` (into `<hillclimb_root>/holdout_eval_v0/`) to obtain `<holdout_score(v0)>`, then present a before/after and ask:
       ```markdown
       ### Replace the existing context set?
       | | Context set | Hillclimbing accuracy | Holdout accuracy | Local file |
       | :-- | :-- | :-- | :-- | :-- |
       | **Current** (`<Final Context Set resource>`) | what is published today (`v0`) | <score(v0)> | <holdout_score(v0)> | `v0/context_set_v0.json` |
       | **New candidate** (`<Draft Context Set resource>`) | best of this run (`vK`) | <score(vK)> | <holdout_score(vK)> (**PASS**) | `vK/context_set_vK.json` |
       Replace `<Final Context Set resource>` with the new candidate? Only the context payload changes — its existing database association is kept (this experiment's database is added to it). The current contents stay on disk in `v0/context_set_v0.json` and can be re-uploaded if you change your mind.
       ```
       - **Yes** → first call `get_context_set(... <context_set_id>)` to read the existing set's current `databases` list and check for concurrent updates since `v0` (if `payload` changed since `v0`, warn the user and confirm before overwriting); then read `vK/context_set_vK.json`, `upload_context_set(... contextSetId=<context_set_id>, contextPayload=<exact file contents>, databases=<**append**: the existing `databases` list returned by `get_context_set` plus the database derived from the Active Database source + tools.yaml, de-duplicated; never send only ours>)` → poll gate → `delete_context_set(... <context_set_id>_draft)` → poll gate (NOT_FOUND = success). Replace `## Finalizing` with `## Final: <Final Context Set resource, exactly as recorded in experiment_state.md> (from vK, score <S>) — replaced previous contents` plus both operation names.
       - **No** → `delete_context_set(... <context_set_id>_draft)` → poll gate. Replace `## Finalizing` with `## Final: not published — <Final Context Set resource> unchanged; best candidate vK/context_set_vK.json (score <S>)`. Offer to publish the candidate under a new name later (that is a new experiment cloned from this one with a new `Context set id`).
     - If the holdout verdict is **not `PASS`** (`INVESTIGATE` or `INCONCLUSIVE`) or `vK` does **not** beat `v0` (`K = 0`, or equal score): do **not** offer to replace `<Final Context Set resource>`. Explain why (either the holdout check returned `<VERDICT>` so the existing production set is kept safe while follow-up happens in a cloned experiment, or no improvement was achieved over `v0`), `delete_context_set(... _draft)` → poll gate, and write `## Final: not published — <reason>; <Final Context Set resource> unchanged; best candidate vK/context_set_vK.json (score <S>)`.
5. **Print the on-screen card** from the Holdout phase (now that the publication state is known), then the *Next experiment hand-off* **unless the verdict is PASS** — see [`../../context-engineering-workflow/references/holdout-evaluation.md`](../../context-engineering-workflow/references/holdout-evaluation.md). Reuse the resource strings recorded in `experiment_state.md`.

**Final output** is the `## Final:` line (resource name or "not published"), the candidate's score and local file, and the generalizability verdict. No `_draft` resource remains on the server when a run is complete.

## Finalize & Server Deletion Rules

- **Strict Target Allow-List & Deletion Scope**: Only delete resources this run created — the single `<context_set_id>_draft` recorded in this run's `experiment_state.md` (existing case only), and only after the replacement decision has been made. **Never delete** a user-supplied seed resource or anything under the bare `<context_set_id>`. In the fresh case nothing is ever deleted. Before every `upload_context_set` or `delete_context_set` call, verify that `(projectId, location, contextSetId)` is one of the identities recorded at `init` in `experiment_state.md` (allow-list: `<working_copy>` during iterations/Finalize, `Final Context Set resource` on existing-case Finalize `PASS` + user yes, or `Seed Context Set resource` strictly on Finalize `PASS` + user yes), and refuse anything else.
- **At-Most-Once Existing Resource Write**: An existing context set under `<context_set_id>` (or an original `<Seed Context Set resource>` in a cloned experiment) is written **at most once** — by the Finalize HITL above, strictly when the holdout verdict is **`PASS`** and `score(vK) > score(v0)`, after evaluating `v0` on `splits/holdout.json` and presenting the full comparison, and only with the user's explicit yes. Never during the loop, never when the holdout verdict is `INVESTIGATE` or `INCONCLUSIVE`, never on auto-approve, never on a resume without re-asking.
- **Database Association Preservation on Replacement**: When replacing an existing `<context_set_id>` (or updating `<Seed Context Set resource>`), always call `get_context_set` first, read its existing `databases` list, append this experiment's derived database (from `## Active Database` + `tools.yaml`), and send the full de-duplicated list so existing database associations are never dropped.
